# Semesta

Voxel action RPG 2.5D in the browser (the in-world town is **Anavela Universe**). three.js + Vite, vanilla JS ES modules. All pixel art (textures, sprites, icons) is generated procedurally via 16px canvas. Music & SFX are fully synthesized with WebAudio — no audio files. Exceptions: `logoasset/semesta.png` (logo) & `logoasset/nxrmascott.png` (mascot) imported by `src/ui/menu.js`, plus two Google webfonts (`Pixelify Sans` body via `--font-body`, `Silkscreen` display titles via `--font-display`, linked in index.html).

Art direction: cozy Stardew-Valley-ish palette (lush greens, warm earth, turquoise water), chibi big-head characters (NOT minecraft proportions), cute-critter enemies/NPCs/pets with big glossy pixel eyes (Pokemon / Pokopia / Animal Crossing energy).

## Running

```bash
npm install
npm run dev      # http://localhost:5173
npm run build
npm run preview
```

## Structure

- `src/main.js` — bootstrap: Opening (menu.js) → Character Creation → **cinematic load screen** (loadscreen.js; `setBoot(pct, label)` now reports a real stage name for every step: opening the canvas → painting the pixel tiles → raising the terrain → carving the coastline and the sea → planting the forest → filling the lakes and the ocean → waking the villagers → **forging every item icon** → **waking the wilds** → **compiling shaders** (`renderer.compile` + one throwaway render) → tuning the orchestra — the last four are a deliberate PREWARM so the first bag open / first swing / first night doesn't hitch. **WAKING THE WILDS is the one that was missing**: `renderer.compile` only knows what is IN the scene, and when the world finishes building that is terrain, village and trees — not one monster, spell or weapon effect. So the compile covered the quiet half of the game and none of the loud half, and the first monster you met, the first skill you cast and the first world boss each paid for a shader compile on the frame they appeared. `enemyMgr.prewarm()` now builds one of every species (plus every boss) 400 units under the camera, one of each particle effect is fired into the same void, everything is compiled and rendered, and then the meshes are thrown away — shared geometry and compiled programs survive, which is the entire point) → build world → game loop; wires the **dual-action interact system** (`gatherInteractions()` collects all nearby actions by priority → `interactPair()` returns a PRIMARY + a distinct-`kind` SECONDARY, so farming's Plant/Harvest never fights a villager's Talk for one button: **F / ★ = primary, R / green ✦ button = secondary**; landmarks beat wandering NPCs, farm plots get their own slot), auto-aim, jump (Space), mounts (M), world map (N), wardrobe (O), **Teleport, TWO destinations** (**T / ⌂ GO HOME** and **Y / ⛺ BASECAMP** — 1.6s stand-still channel, 20s cd; home lands via `moveToClearSpot` on a clear cell BESIDE the house door, basecamp always lands on `terrain.spawn`, and home falls back to the basecamp if you own no house. They are separate because they are wanted at different moments — the shops, forge and gacha are in town, your crops are at home — and one button meant that once you owned a house you could never fast-travel to town again), AFK fishing (G), **AFK Auto-Battle (B / ⚔AUTO)**, world boss scheduler (180s), safe zones (village/camps/homes — `inSafeZone`), economy/cooking/estate APIs, **gacha v2** (six-tier weighted roll + soft pity `gacha.pity` — +weight to epic+ after 8 dry rolls; tier pools in `GACHA_POOLS`; owned uniques refund coins per `RARITY[r].refund`), **level-up celebration** (`levelRewards`: coins every level, tonics each 3rd, an unowned cosmetic each 5th, golden shockwave/fountain FX + `hud.levelUp` overlay + `levelup_big` fanfare), out-of-combat auto-heal, save v3 (now incl. `wardrobe`, `gachaPity`); `decor.clearArea` is called for camps/landmarks/lands at build & after `estate.build` so scenery never clips structures, and `moveToClearSpot` frees the player from fresh house footprints
- `src/ui/docs.js` — **THE SEMESTA GUIDE**, reachable from the main menu (📖 HOW TO PLAY) *before* you commit to a character, because a new player's questions all arrive before NEW ADVENTURE. Categorised sidebar (GETTING STARTED / THE WORLD / CORE SYSTEMS / LIVELIHOODS / PROGRESSION / ECONOMY / GAMEFI / HELP) + long-form sections, built from ONE `CATEGORIES` data array so a topic is one entry not two; `call('do'|'dont', …)` callouts and `kv()` tables. **27 sections** (added ATTRIBUTES and LIFE SKILLS, which the game had and the guide did not). The GAMEFI chapter states plainly that **nothing is on-chain yet** and that anyone asking you to connect a wallet today is not us — a guide that oversells is worse than none. - `src/gfx/signs.js` — **signboards**: a 5x7 bitmap font defined in-file (not `fillText` — the webfonts may not have loaded when the world builds, and a real bitmap font upscales to crisp blocks) plus `makeSignTexture(label, glyph, accent)` painting a three-plank board with carved lettering and a tiny pixel pictogram. `buildSignboard()` in npcs.js hangs it from two posts on chains. It was only reachable after a delete until the sign-in flow started rebuilding too, at which point the strip was dead from the moment the menu appeared for anyone already signed in. Verified with a control in the same page: bound the old way a probe fires 1 → 1 across a rebuild, the new way 1 → 2. `charselect.js` already binds to its surviving root. Per-row hint line explains what each knob actually costs
- `src/systems/story.js` — **THE STORY OF ANAVELA**, in 7 chapters. The arc: you are the last apprentice of the **Lanternkeepers**, the order that kept Anavela's lights burning; the lights went out, the wilds walked back in, and relighting them is how the world is put right — ending on "we were never keeping the dark out, we were keeping the place worth coming back to". Every chapter gates on a condition the game ALREADY tracks (level, kills, `swam`, `visitedIsland`, `hasHome`), so `story.check(ctx)` is called once a second with live state and the story advances by PLAYING rather than by scripted triggers. Each beat pays a reward (the finale hands over the Nimbus mount) and sets `state.hint`, the one-line nudge for what to do next. `hud.showStory` renders it as a parchment-and-gold card that **waits for the player** — it used to dismiss itself after 16 seconds, so the card vanished mid-sentence; a story beat that deletes itself while you are reading it is worse than no story. It now closes only on CONTINUE, carries a `NEXT ·` line naming what to do, and `hud.getStoryLog()` keeps every chapter shown, and it counts as a menu overlay so it blocks the mobile joystick
- `src/systems/gamepass.js` + the pass tab in `src/ui/panels.js` — **GAMEPASS, and it now has a SEASON.** A pass that never ends is a very long quest, and it is the whole reason nobody felt any urgency about one. **`seasonNow()` derives the live season from a fixed epoch** (1 Aug 2026 UTC, `SEASON_DAYS` 30) rather than from a server, so every client agrees on which season it is with nothing to deploy, and a save that has been shut for two months lands on the correct one the moment it opens. Four seasons rotate — THE LANTERN ROAD / TIDE AND EMBER / THE LONG FROST / HOLLOWTIDE, each with its own name, blurb and accent colour. `rollSeason()` is checked on load and once a second in the game loop: on a boundary the xp, the claims AND the pass itself reset, because a pass you keep forever is a purchase you make once. **THE TRACK IS BUILT PER SEASON, and the split is deliberate: the SHAPE is the tuned part and never moves** (which tiers are milestones, where the grand prizes land, how the coin curve climbs) while `buildTrack(seasonIndex)` rotates WHAT lands on those beats out of `POOLS` by season index — same season, same track, on every machine. Measured: 15 of the 90 reward slots differ between two seasons, which is every big/grand beat. **THE LADDER TAKES REWARD NAMES FROM `ITEMS`, NEVER FROM A HAND-WRITTEN LABEL** — the panel prints the name beside every icon now, and a swept check found five already wrong ("Halo" for Radiant Halo, "Gilded Crown" for Royal Crown, "Sprout Pack" for Sprout Wings). `name()` looks up anything with an id; the written label only survives where there is nothing to look up (coins, a `weaponTier` that resolves to your class at claim time). The same sweep across all four seasons caught four invented pet-charm ids (`charm_kit`, `charm_pip`, `charm_tuk`, `charm_bibi`) that would each have granted a nonexistent item. **Re-run it after touching the pools.** **BASIC AND PREMIUM ARE UNLOCKED WITH AN ITEM FROM PIP'S SHOP, not a gold button in a menu** — `pass_seal` (Keeper's Seal, 1,000c) and `pass_sigil` (Keeper's Sigil, 3,000c), with the Sigil priced at the DIFFERENCE while you already hold Basic. `buy(kind, spend)` is gone; `activate(kind, consume)` takes the item out of the bag. It gives the shop something to be for, makes unlocking a pass a thing you went and got, and is the exact shape a token purchase would take later: a deterministic item, not a roll. **`sail` and `island` were fired by main.js and worth ZERO** — an event with no weight in `PASS_XP` is silently dead, which is precisely what makes an XP system feel arbitrary; both carry a weight now, and `PASS_XP_LABEL` gives every action a plain-English name so the panel's HOW IT WORKS tab is generated from the real table rather than described next to it. `weaponTier` rewards resolve to the family matching YOUR class (axe and cannon borrow the closest silhouette rather than granting nothing). Rewards stay claimable retroactively for every tier reached, with a CLAIM ALL. Same contract as dailies: rewards are DATA here, granted by a caller-supplied `grant()`
- **THE WHOLE SEASON WAS FIFTY MINUTES LONG, AND THAT WAS MEASURED.** The first pass was 30 tiers at a FLAT 100 XP: 3,000 XP total. Against the real `PASS_XP` table at plausible rates that is **50 minutes of auto-battle** (15 kills/min x 4), 55 of ordinary mixed play, 75 of world bosses — a thirty-day season finished in under an hour, with nothing after it. Two causes, both fixed. (1) **A FLAT COST MEANS TIER 50 IS AS CHEAP AS TIER 1**; `xpForTier` now climbs 120 -> 1,198 across **50 tiers**, `TOTAL_XP` **32,950**, which measures to ~9.2h of grinding or **~20 min/day** over a season. (2) **A TRACK THAT ENDS IS A TREADMILL THAT STOPS**: past the last tier every `PRESTIGE_XP` (1,500) is an endless **KEEPER'S CACHE** paying a token, gold and forge stones, so the last week of a season is still worth playing. `tierOf`/`progressInTier`/`toNext` read a cumulative `CUM` table rather than dividing, and `event()` is deliberately UNCAPPED. Re-run `xpForTier`/`TOTAL_XP` against the XP table after touching either
- **THE KEEPER'S VAULT — the pass's own spin, and deliberately the OPPOSITE of the gacha.** Two identical slot machines is one slot machine, so **the Vault never hands you a piece you already own**: `spinVault` picks uniformly from what is MISSING, which makes 6 tokens the whole set every single time. It still reveals like a spin — that is the fun — but it cannot waste your token, which is what makes it read as a reward rather than a bet. Once the set is complete a token rolls `VAULT_BONUS` (mythic weapon / 1,200c / 10 forge stones) so a token is never dead. **`pass_token` (Keeper's Token) cannot be bought at any price** — the only sources are the track (2 free / +3 basic / +5 premium) and the caches, which is what stops the Vault being a second shop. Same contract as everything else here: `spinVault(consume, owns)` takes both predicates from the caller and never touches an inventory. **21 -> 6 new pass-exclusive cosmetics carry `limited: "Keeper's Vault"`** — Lumenwreath, Keeper's Regalia, Keeper's Mantle, Constellation Wings, Lumen Trail, Gilded Dust — and they are the most worked pieces in `cosmetics.js` on purpose: the Regalia is built from the same three parts the world's stone lanterns are (band, spire, LIT PANE between the spires, never on one), the Lumenwreath touches the head at no point and is five caged flames orbiting above it, the Mantle hangs seven lanterns on their own pivots along the hem, and the Constellation Wings are STARS JOINED BY LINES rather than feathers. **Their icons are hand-drawn in `ICON_MAPS`, not left to `paintCosmeticIcon`** — that painter makes a lozenge tinted by slot and rarity, which is fine for the fortieth hat and is the entire "items look too simple" problem when it renders at 46px in the shop window for the premium track
- **THE FILLER SIGNATURE MISMATCH THAT MADE THE WHOLE LADDER ONE REWARD.** `buildTrack` calls `(SHAPE[k][i] || FILLER[k])(S, i)` — milestones and fillers get the SAME two arguments. `FILLER` was written taking `(tier)` alone, so it received the SEASON INDEX, which is 0: `0 % 5 === 0` made **every free filler a Forge Stone x4, every basic filler 180 coins and every premium filler a Lucky Charm x3**. Every id was real, so the id sweep passed and the track was simply the most boring ladder ever built. The validator now also checks VARIETY — distinct labels per row, and no single reward on more than 40% of tiers — because "all ids resolve" was never the property that mattered. Currently 37/28/31 distinct of 50
- **THE PASS PANEL IS THE PRODUCT, and it is the one screen in the game that has to sell something.** It was a strip of 38px icon squares with `title` tooltips at 7px, which never said what a reward was, what a season was, or what the difference between the rows was. It is now **820px wide** (every other panel is 500) with a season hero block, three comparison CARDS stating exactly what FREE / BASIC / PREMIUM each give, a **50-row ladder where every reward shows its name at 10px next to a 30px icon**, the endless-cache row at the bottom, and three tabs — TRACK / THE VAULT / HOW IT WORKS, the last generated from the live `PASS_XP` table rather than described next to it. **ONE SCROLLER, AND A STICKY BAR — measured, not guessed.** The header (season hero + three cards) is ~480px of a ~700px panel, so an inner scrolling ladder got 150px and fought the outer one at the seam; the PANEL scrolls once and a slim `.psticky` bar carries tier / XP / tokens / tabs, with the column header parked under it at an offset read off the bar's real height. Verified live: 820px wide, 0 horizontal overflow, 50 rows x 3 chips, 0 empty names, 0 clipped names, 0 broken icons, current tier scrolled into view, and 6 vault spins returning 6 distinct pieces with 0 duplicates
- `src/systems/index.js` + `src/ui/indexpanel.js` — **THE INDEX**, the collection log and the answer to "at max level this game has no target left". **145 entries across 7 categories** (fish 14 / pets 17 / mounts 8 / monsters 14 / bosses 6 / weapons 41 / wardrobe 45), and the catalogue is **DERIVED** from ITEMS, PET_DEFS, ENEMY_TYPES, WORLD_BOSSES and MOUNT_DEFS at load, so anything added to those tables appears automatically and cannot be forgotten. Discovery is a FACT not a reward: `see(cat, id)` is called from where the thing happens and grants nothing; category completion pays out through a caller-supplied `grant()` (same contract as dailies/gamepass). **Everything you can HOLD is logged off the bag** in one `inventory.onChange` sweep rather than at eight separate grant sites — fishing, chests, gacha, quests, the pass, dailies, level rewards and the shop all land in the same place, including reward paths added later. Monsters and bosses log on the KILL (`onKill`), because a log that filled from the spawner would be complete before you fought anything. An unfound row shows its rarity colour, a **blacked-out silhouette of the real art** and a hint ("Out at sea, after dark") — the empty rows are the content. `see()` rejects ids not in the catalogue, so a typo can never produce an unreachable 15/14. Old saves are backfilled from the bag on first load. NOTE: the bag is `inventory.state.materials` and it is a **Map** — reading `Object.keys(state.items)` silently logged nothing forever
- `src/systems/dailies.js` — retention trio sharing one save blob: **30-day check-in** (`CHECKIN_DAYS`, escalating rewards — coins/mats early, cosmetics at d7/14/20/21/26/29, **Pebble mount at d30**; rolls over at local midnight, a >1-day gap resets the streak), **play-time milestones** (`PLAYTIME_TIERS` at 5/15/30/45/60 min, per session) and a **daily quest board** (3 drawn from a 12-quest pool by a day-seeded shuffle so refreshing can't reroll it). Rewards are described here as data and granted by a single caller-supplied `grant()` — the module never touches the inventory. main.js feeds it `kill/boss/fish/chest/gather/plant/harvest/cook/forge/skill/gacha` events and `hud.setMenuBadge(dailies.pending())` pulses a "!" on ☰
- `src/ui/loadscreen.js` — **cinematic loading screen**: five procedural pixel VIGNETTES (320x180 canvas upscaled `pixelated`, one picked at random per boot) — **dawn** over the village (climbing sun, drifting clouds, birds, chimney smoke), **night** on the lantern road (stars, cratered moon, glowing stone lanterns, dancing fireflies), **winter** (drifting aurora bands, frost conifers, snowfall), **sea** (sunset ocean, island silhouettes w/ leaning palms, scrolling wave bands, a jetski cutting a wake), **festival** (bonfire w/ stacked flame tongues, swaying chōchin, 4 chibi critters hopping, rising embers). Shared grammar: sky gradient → layered silhouette ridges → one focal element → one particle system. Over it: the SEMESTA wordmark, the scene's name, an HONEST 24-cell segmented bar driven by the real build stages (not a timer), a rotating DID-YOU-KNOW tip that doubles as a soft tutorial, scanline+vignette veil, and the BUILD FOR RIALO line. `createLoadScreen({logoSrc, vignette})` → `{ el, stage(label, pct), done(), dispose() }`
- **THE PLAYER ARROW WAS INVISIBLE ON SNOW, AND THE WORLD MAP'S POINTED BACKWARDS.** The snow tile is `#e8f0f5` and the arrow was `#f0f0e0` — the same brightness — so in the winter biome the one marker you navigate by simply vanished. Measured on the real tile colour: **0 pixels** differing from the ground, peak contrast 0.2/255. It was also the only marker in `minimap.js` without a dark outline; the house, the boss diamond and the waypoint flag all stroke `#5e3c10`, which is exactly why they were the ones that never disappeared. A stroke UNDER the fill is the fix rather than a drop shadow: it casings every edge equally, so the arrow reads on white snow and dark forest with the same shape whichever way it points. After: 135 pixels differ, peak contrast **216.6**. Separately, `worldmap.js` draws its own arrow and still had the 180-degree fault minimap.js had already fixed and documented — `toXY` maps world z straight to canvas y, so `rotate(-facing)` sends the tip to `(-sin f, -cos f)`, the exact negative of the heading. Checked against all four cardinals: **4/4 backwards**. Both now use `PI - facing`
- `src/ui/worldmap.js` — fullscreen world map overlay (N / tap minimap): village ⌂, camps ▲, land ◎ w/ "FOR SALE"/"YOUR LAND" labels, built homes as big pulsing ⌂ + "YOUR HOME" label, quest !, boss ◆, player arrow; **tap the map to drop a ⚑ waypoint mark** (tap it again to clear) — `getPin()/clearPin()`; main.js shows a HUD beacon chip (camera-relative arrow + distance via `hud.setBeacon`), draws the flag on the minimap, and auto-clears w/ a toast when the player arrives (<2.5u); explicit ✕ close button (backdrop click also closes — clicking the map no longer closes it)
- `src/world/camps.js` — 6 rest camps (campfire+tent+bench, quadrants + sparse mid-edges) each with a Ranger fox-NPC (talk → full heal): safe zones, fast heal, cooking stations
- `src/world/gather.js` — gatherable nodes: pale banded BIRCH trees (chop → hardwood) & glowing-vein ORE boulders (mine → iron ore/forge stones), 3 hits, respawn
- **CALM WATER**: the two lakes (radius + 5) and are registered as sanctuaries in `inSafeZone`, so the enemy AI's existing rules apply — no spawns, repelled at the boundary, aggro'd monsters disengage and wander off. Verified: 61 monsters force-spawned at the zones, **0** ended up inside one
- `src/systems/farming.js` — 8 farm plots by the village (2 free, buy more): plant seeds → 3 growth stages → harvest crops to sell
- **A HOUSE TAKES TIME NOW, ON THE WALL CLOCK.** Building was instant, so the whole estate ladder was over in one sitting — which is the shape of a game somebody finishes in an afternoon and never opens again. Each rung books a finishing TIME (`buildMs`: cabin 20m, cottage 4h, villa 12h) stored as an ABSOLUTE timestamp, so it counts down with the game shut; a timer that only runs while you watch it punishes playing. The materials are taken at the START and a `buildSite` goes up in place of the house — scaffolding, a part-raised wall in the tier's colour, a ladder and tools — because a timer with nothing to look at is a locked door with a clock on it. Verified both ways: reload mid-build and the site is still there counting down; reload after the time passed and the house is standing
- `src/systems/housing.js` — **THE HOMESTEAD: one house, one place, three tiers.** There used to be 4 land parcels at 250c scattered across the mainland, and it was the weakest system in the game — four identical plots is a choice with no content in it (whichever you walked past first became yours and the other three stayed as signposts advertising something you already owned), and the three designs were ALTERNATIVES rather than a ladder, so picking the Villa meant never seeing the other two. There is now exactly ONE buildable site and it is yours from the first minute: **Lanternhome** (`terrain.islands` entry `kind: 'home'`, the nearest island to the mainland so the crossing is swimmable), with a laid foundation, a builder's post and a stack of timber. `HOUSE_TIERS` is a ladder climbed ONE rung at a time — 1 Driftwood Cabin (12 hardwood/4 ore) → 2 Anavela Cottage (28/12/200c: chimney, window boxes, picket fence, two path lamps, stepping stones) → 3 Lanternkeeper's Villa (45/22/600c: two storeys, balcony, stone wall + gate, well, and **a beacon on the ridge that burns all night** — the one part of the build that is not domestic). Each rung changes the whole PLOT, not just the roof. A house is rigid flat geometry and the villa's yard wall reaches 3.5u out, so `terrain.js` levels the middle of Lanternhome (`HOME_FLAT` 7, eased to 12) — measured drop **0.89 → 0.000** across both the footprint and the yard wall, 0 wet cells. `lands` stays an array of ONE so the world map, minimap and safe zones keep working unchanged. `load()` reads BOTH formats: a v3 array of parcels resolves to the best house anybody built. The module never touches the inventory — `estate` in main.js owns the cost, same contract as dailies/gamepass
- `src/systems/skilltree.js` — **LIFE SKILLS**: fishing, farming and cooking each level on their own XP and pay a point per level, spent on a small tree. Nodes have to change how the activity PLAYS, not add a hidden percentage — a wider bite window, a second fish on one cast, an extra crop, the seed back, a plant left standing, two portions from one pot. **Mythic fish are gated behind a single 3-point node**, the only thing in the game that unlocks them. Everything is data plus `bonus(skill, key)`, so callers ask "how much extra?" and never need to know what a node is. Panel: ☰ → LIFE SKILLS or **L**
- `src/world/wind.js` — **WIND**: ONE vector that wanders in heading and strength and throws occasional gusts. There are deliberately **NO drifting motes** — a first pass carried leaves across the screen and they read as debris ON THE CAMERA rather than in the world, constantly crossing the middle of the view in a game you are trying to aim in. Wind is better felt through what it MOVES than through litter flying past your face. The point is that everything leans off the SAME source (Rialo banner, paper lanterns, flower beds) — that coherence is what separates weather from every prop wobbling on its own private sine. `sway(phase)` hands out a value already in the right rhythm; mote count scales off the weather budget and reaches zero at the bottom of it
- **THE FIGHTER** (7th class, `weaponType: 'fist'`) — the only class with no weapon. `fist` is a REAL weapon type, not a re-skinned dagger: its own 4-tier crafting line (Hand Wraps → Rattan Guards → Iron Knuckles → Harimau Claws), its own icon painter, its own reach (1.6, the shortest in the game) and `hits: 3`. The basic attack is a **three-beat combination** — jab off the lead hand, cross with the hips turning through it, then a knee off a small hop — and `doAttack` fires three separate damage beats on the animation's own timings (0.16 / 0.44 / 0.78 of the swing, at 0.85x / 1.0x / 1.35x), so the knee is audibly and numerically the payoff. Both hands are wrapped (the weapon exists TWICE; a Fighter with one glove is a Fighter who lost a glove). Skills: `flurry` (six staggered punches — one lump of damage would be a Bash), `risingknee` (dashes to the target first, because a knee that only works when you are already touching something is a knee nobody presses) and `ironbody` (raises the damage-reduction ceiling from 0.6 to 0.75 while active, the one window where standing still is survivable). - **FACING CONVENTION** (get this wrong and everything moonwalks or crabs sideways): headings use `atan2(dx, dz)` and movement is `(sin d, cos d)`. A mesh whose forward is **+Z** (bunny, deer, turtle, every enemy) sets `rotation.y = d` directly. A mesh whose forward is **+X** (fish, gulls) needs `d - PI/2`, and on a `(cos a, sin a)` orbit it is `-a - PI/2`. Enemy `e.dir` used the maths convention (`cos`→x) while every `rotation.y` in the file used the other, and the WANDER branch never set a facing at all — which is why wandering monsters slid sideways

## Renderer performance — measured, and what is still owed

Benchmarked against SeismicSkate (React Three Fiber, same author). That project
is a single skate park and Semesta is a 200-cell open world, so the workloads
are not comparable — but three of its choices were straightforwardly better and
are now adopted.

- **AMBIENT OCCLUSION (N8AO), and the version floor that gated it.** Bloom adds light; AO takes it away where light could not reach, which is what makes a corner read as a corner and a prop sit ON the ground instead of hovering. It sits AFTER the scene and BEFORE bloom — running it the other way rounds the glow back into the creases AO just deepened — at half resolution, because occlusion is a soft wide signal. Getting it required a **three upgrade**: n8ao is built on pmndrs `postprocessing`, which requires three >=0.168 <0.186, and Semesta was on 0.166.1. That upgrade was safe specifically because Semesta has **no custom shaders anywhere** (no ShaderMaterial, onBeforeCompile or RawShaderMaterial) and never touches outputColorSpace/encoding, so neither the shader-chunk nor the colour-management breakage applies. Radius solved by sweeping against the real frame, measured as the shaded fraction of the plaza: no AO 1.3%, r1.6 2.0%, r4 3.2%, r8 4.5%, r20 5.8% — settled at r6/intensity 4, because past ~14 the radius exceeds the props it is meant to ground and the frame just gets murkier
- **AO IS OFF BY DEFAULT, and the white haze that put it there was DOUBLE GAMMA.** `N8AOPass` assumes it is the last pass writing to the screen and does its own linear-to-sRGB conversion; the `OutputPass` behind it already does that plus the tone map, so the frame was gamma-corrected twice and came out a milky white wash over everything. `configuration.gammaCorrection = false` is the fix, with `transparencyAware = true` alongside it because this world is full of additive sprites that a plain depth buffer would ring with dark halos. It stays opt-in (`__semesta.aoPass.enabled = true`) until somebody LOOKS at it — a change to how the game looks does not ship as the default on the strength of a brightness average
- **MEASURE A POST PASS BY ITS PARAMETER, NEVER BY `pass.enabled`.** Toggling a pass off changes which ping-pong buffer EffectComposer reads from, so an A/B on `enabled` compares two different images — it reported AO making the scene 79 levels BRIGHTER. Sweeping `configuration.intensity` from 0 keeps the chain identical and gives the true delta
- **ADAPTIVE RESOLUTION.** The preset picked a render scale ONCE at boot from
  `hardwareConcurrency`/`deviceMemory`, which say how many CPU cores a machine
  has and nothing about its GPU, its thermal state or how heavy the part of the
  world you are standing in is. A fixed guess is either too low or drops frames
  and never recovers. The frame is timed around the draw now and the backing
  store follows it: median of ~45 frames (never one hitch), steps of 0.1, a
  one-second cooldown, floor 0.55, and it never climbs past the preset own
  scale. Render scale is QUADRATIC on fill, so 1.0 -> 0.8 removes 36% of every
  fragment including shadows and bloom. This is the lever that makes a frame
  budget a promise rather than a hope.
- **BLOOM AT HALF RESOLUTION.** UnrealBloomPass is not one pass — it is five
  downsamples, five upsamples and a composite, each a full-screen draw. At
  backing-store size that is eleven full-frame passes on top of the scene. Bloom
  is a wide soft blur by construction, so half-res is visually near-identical
  and costs a quarter of the fragments. Measured: 640x360 against a 1600x900
  screen, about one sixth of the previous fill.
- **`powerPreference: 'high-performance'`** — without the hint a laptop with
  switchable graphics runs WebGL on the integrated chip, which is the machine
  most players are on.
- **WEBGL CONTEXTS ARE LOST, AND WITHOUT A HANDLER THE SCREEN STAYS BLACK FOREVER.** A driver hiccup, a laptop switching graphics chips, or the OS reclaiming the GPU all kill the context — and the browser only attempts to restore one if the page calls `preventDefault()` on `webglcontextlost`. There was no handler at all, so any of those turned into a black canvas with the game still running behind it and no way back but a reload. The loop now skips the draw while the context is gone (rather than throwing once a frame) and `applyPixelRatio()` rebuilds the backing store and every pass target on restore. NOTE this was NOT proven to be the flicker players report: a per-frame sampler over the composer's screen output found **0 dark frames** across idle play, adaptive-resolution steps in both directions, a window resize and LOW/ULTRA preset switches. It is a real gap worth closing, not a confirmed diagnosis
- **THE BLACK FLICKER WAS THE RESIZE ITSELF, NOT THE RENDER.** Assigning `canvas.width` — which is what `renderer.setSize` does — reallocates the drawing buffer and clears it to transparent black. Measured: brightness **52.2 before an adaptive step, 0.0 immediately after, on 6 of 6 resolution changes**. Nothing was wrong with the frame that got drawn; the hole is the gap BETWEEN the resize and the next draw, and if the compositor lands in it the screen blinks. That is why sampling after `composer.render` found nothing wrong — it was looking at the only moment that was always fine. `applyPixelRatio` now paints a frame into the buffer it just cleared, guarded by a `canRedraw` flag that is armed once the world is built. Verified: 6/6 steps blank before, **0/6 after**. This is also why the flicker is NEW — adaptive resolution came in with the perf pass, and before that nothing resized mid-game
- **AND THE SCALER WAS HUNTING.** The thresholds were adjacent (down above 20ms, up below 13ms), so a machine sitting near the boundary chased itself — step up, get slower, step down, get faster — and every step is a reallocation and therefore a chance to flicker. The dead band is 11-22ms now and a step needs the median outside it for TWO checks running, which no oscillation satisfies; the cooldown is also asymmetric (1.5s down, 3.0s up) because dropping quality under load should be quick and taking it back should not start a new oscillation
- **THE AUDIT SWEEP, and what it is worth re-running after any big change.** Seven passes, all against the live game: (1) every visual builder — 20 enemies, 12 bosses, 17 pets, 8 mounts, 217 item icons, 0 failures; (2) all 48 skills cast and all 7 class trees resolve, every node a real skill; (3) all 90 dungeon floor plans (30 x 3) — 0 empty floors, 6 distinct bosses reachable, HP curves monotonic (easy 0.94 -> 5.12, hard 2.01 -> 10.88), 0 dead reward ids; (4) all 14 panels open and close leaving no stuck `busy` and no leaked DOM; (5) a save/load round trip losing 0 fields; (6) a four-floor dungeon run including a warden, each floor populated and cleared only on kills; (7) a soak with waves, a day/night sweep and every skill — **0 new shader programs and the visible light count pinned at 11**, which is the old stutter cause still staying fixed
- WHEN AUDITING FOR LEAKS, THE AMBIENT SPAWNER WILL FOOL YOU. A wave test reported meshes climbing +114/+220/+323 and "MESHES ACCUMULATING" — wrong. The spawner refills the world faster than a test kills it, so the residue was 27 monsters that genuinely existed. Kill EVERYTHING (not just what the test spawned), settle, and compare against live enemy count: it comes out at ~5 meshes per live monster with **0 orphaned enemy roots**, and returns to baseline. Also kill through `enemyMgr.damage(...)`, not by setting `e.dead = true`, or the disposal path never runs
- WHEN TESTING ANYTHING GATED ON BOOT: `window.__semesta` is assigned BEFORE the last few lines of `main()`, so a test that polls for it can run while flags set at the very end (`canRedraw`) are still false. That produced one false "the fix does not work, still 6/6 blank" report
- MEASURING BLACK FRAMES: sampling the default framebuffer after `renderer.render` inside a composer chain reports 50% black and means nothing — that is `RenderPass` drawing the scene into an OFFSCREEN target, and the screen buffer legitimately has nothing in it yet. Only judge a frame when `renderer.getRenderTarget() === null`, and only wrap the OUTER `composer.render`. Cost one false "half of all frames are black" report
- **ONE PATH FOR RESIZING.** The resize listener sized the renderer and composer by hand and skipped everything else `applyPixelRatio` does — the adaptive ratio, the half-resolution bloom, the AO target. Two code paths that must agree about render-target sizes is the exact shape of the mismatch that produced black frames the first time, so the listener calls `applyPixelRatio()` now and there is one
- **SHADOW CASTERS ARE GATED BY RANGE.** The sun s shadow camera is 60 units across; 338 objects carried `castShadow` and 242 of them sat further than 45 units from the hero, where nothing can ever reach the depth map. The flag is now driven by distance, riding along on the light tick that already traverses the scene — one comparison per object, no extra pass. Measured: **338 casters down to 62, none beyond range**, draw calls 476 to 441
- **THE WORST FRAME IS THE MOST COMMON ONE, and it was a coverage gap.** Draw calls measured from four places: an open field 125, a flower bed 236, the coast 1,297 and the **VILLAGE PLAZA 1,399** — where you spawn, where the shop, forge and gacha are, and where players spend most of their time. The cause was not density but COVERAGE: every builder bakes its own list (`npcs.js` bakes `placed`, landmarks `built`, isles bins per island) and anything added straight to the scene outside those lists is never merged. Measured, one 61-mesh village subtree with nothing animated in it was costing 62 draw calls, one per mesh. A per-builder list is a thing somebody has to remember to add to, **the obvious fix is wrong and shipped broken for one commit**: a sweep that walks the finished scene and bakes every static top-level child pulled houses apart and left pale slabs of building scattered over the grass. `bakeStatic` is built to be handed ONE STRUCTURE — it merges everything under the root into the ROOT'S frame and then removes the originals from their parents. Several top-level children are container groups holding many separately-placed buildings, and some of those are still referenced and repositioned afterwards (docks, houses, anything `moveToClearSpot` touches), so merging a container flattens them all to its origin and empties the groups the rest of the game is still holding. **The gap has to be closed where structures are BUILT** — by handing each builder its own list — not by a sweep that cannot tell a building from a bag of buildings
- NOTE ON MEASURING DRAW CALLS: they move with the camera, the clock and how many monsters are alive, so **only compare numbers taken in the same session from the same spot**. Two readings of the plaza in different sessions came out 1,399 and 526 with no code change between them
- **ONE SWAY PIVOT PER FLOWER BED, not fifty-eight.** Every plant carried its own sway on its own phase, which made all 58 of them ANIMATED PIVOTS — and `bakeStatic` bakes each posed pivot separately in its own frame, so a bed that should merge into a handful of meshes came out as 228, and all 58 were posed every frame on top of that. The bed sways as ONE now and only a sunflower head still turns (it tracks the sun, which is a reason). This is also more correct by the game s own rule: `world/wind.js` says everything must lean off the SAME vector, because that coherence is what separates weather from every prop wobbling on its own private sine. Measured per bed: **meshes 317 -> 129, animated pivots 125 -> 32**; scene-wide geometries 2,731 -> 2,496 and materials 1,863 -> 1,509
- CORRECTION TO THE STATIC AUDIT BELOW, and it is why measuring beat counting: the 564 raw allocation sites are NOT where the cost is. player.js has 242 of them and contributes **31 meshes and 18 materials** at runtime, because there is one player and most sites are conditional. The next real win there is INSTANCING identical baked plants rather than deduplicating anything

## Multiplayer & accounts (live)

- `server/` — the authoritative half, running on a VPS behind a Cloudflare Tunnel. Owns the clock, weather, monster spawning and AI, the world boss, shared farm plots and chat. **The map is never sent**: every client generates a byte-identical world from fixed seeds, which is why one small box is enough. Interest management caps each player's feed at a 70-unit radius; positions go out at 8Hz as TARGETS, and the client eases between them
- `src/net/` — `auth.js` (Supabase: Google sign-in in-page via ID token so the consent screen names the game, not the database). **THE ACCOUNT CARRIES ALL THREE SLOTS, not one save**, and getting this wrong did not merely fail to sync — it DELETED heroes. Two faults compounded: the cloud was only consulted after CONTINUE was pressed, and CONTINUE is drawn from localStorage, so a phone that had never run the game had no button to press and could never ask for the save; and with NEW ADVENTURE the only way in, the fresh hero made there was uploaded a minute later over the row holding the hero from the other device. Now the row holds `{v:4, slots:{}}` (v3 single saves still load as slot 0), the sync runs BEFORE the menu paints and again the moment a sign-in lands, and every upload MERGES against what is already up there so a device never erases a slot it has not seen. The merge rule lives in ONE exported pure function, `planSync`, because this code can destroy somebody's character and "it looked right" is not good enough — 17 cases are tested against it directly. Two rules matter most. **ONE HERO IS NOT A QUESTION**: the prompt was firing on nearly every tab switch, showing "Lv 31" against "Lv 31" eleven seconds apart — one character whose local autosave (8s) is simply fresher than the last cloud upload (60s), which is the NORMAL state and always lands inside the 1.5s-5min ask window. Asking is only honest when taking the newer copy would LOSE something, so same-hero pairs now compare PROGRESS (level, then xp, then coins) and only ask when the newer save is behind. Two causes stacked there: `onAuthStateChange` also fires for TOKEN_REFRESHED, and Supabase refreshes on tab focus, so every alt-tab ran a full sync — the menu now re-syncs only when the user IDENTITY changes. And: **two different heroes are not two versions of one hero.** A timestamp only answers "which is newer", which is right for one character saved twice and completely wrong for two different characters sharing a slot number — someone who plays as a guest and then signs in has a brand new Lv2 that is genuinely newer than the Lv30 in the cloud. They are not in competition, so the incoming hero is rehomed to a free slot and both survive; only when all three are full is there a real choice, and then the player makes it. Deletes carry a tombstone so the next sync cannot resurrect them; `deleteCloudSave` is account-wide (DELETE PROFILE) and `deleteCloudSlot` removes one hero. `client.js` (reconnecting WebSocket; being offline is a normal state, not an error), `remote.js` (other players built with the SAME `buildCharacterMesh` as the hero, so their outfit is really theirs; walk animation derived from distance moved so no animation state crosses the wire)
- `src/systems/friends.js` — **FRIENDS**, deliberately scoped: the list lives on YOUR device and is not yet reciprocal, because the server carries no request/accept and could not be redeployed on launch day. Click any remote body (same raycast Spider uses, checked BEFORE her) → a card with their name, level and ADD FRIEND. Rows sort online-first off `net.state.players`, so "online" means exactly what the HUD population chip means. A returning friend arrives with a NEW connection id, so entries re-link by NAME and refresh their level — loose on purpose: two people sharing a display name merge, which is an acceptable trade against demanding accounts before you can wave at someone. The panel says plainly that adding does not notify them. Written so only `add()` changes when the server ships the handshake
- `src/gfx/qr.js` — a **real QR encoder**, written out because the house rule forbids asset files and CDN libraries. Byte mode, EC level M, smallest fitting version, all eight masks scored for the lowest penalty per the spec, 4-module quiet zone (a QR bled to the edge of a dark panel is the classic reason one will not scan). Used by the About card to point at the live build. **Verified by DECODING IT BACK, not by looking at it** — 29x29, version 3, payload reads `https://semesta-gray.vercel.app/` exactly
- `src/ui/chat.js` — world chat: fades when idle, and remote text is inserted with `textContent`, never `innerHTML`. **The element is parented to `document.body`, not to `#hud`** — `#hud` carries `z-index: 10` and therefore its own stacking context, so chat's `z-index: 40` was scoped INSIDE it and could never rise above `#touchui` at 20; the button was drawn, sat under the joystick zone, and every tap on it moved the character. Position in the tree, not the number, was the whole problem — it now sits at z 30, above the touch controls and below dialogs (40) and the map (60). There is a real **💬 CHAT button** (Enter is only a desktop shortcut): on a phone it is a 46px icon pinned into the measured gap between the HP plate (ends x=188) and the minimap (starts x=269), the one patch of screen no gesture zone claims, and while typing the input box **pins to the TOP** because the on-screen keyboard covers the bottom ~300px
- `src/net/remote.js` — other players, built with the same `buildCharacterMesh` the hero uses. Positions arrive 8×/s and the screen redraws 60×, so every body EASES toward its target and derives its walk from how far it actually moved — no animation state crosses the wire. Also carries **their weapon, their pet, their swing and their speech**: `applyGear` calls the rig's own `setWeapon` and builds the pet from `PET_BUILDERS` (both looked up in OUR tables, so an id we don't know draws nothing); a swing is TRIGGERED by `p.a === 'atk'` and then plays out locally at full framerate (reading the flag as a pose gives a three-frame twitch); pets are parented to the SCENE and trot to catch up rather than being bolted behind their owner like a trailer; chat floats as a canvas **speech bubble** over the speaker's head (`say`), and `sayLocal`/`bindSelf` do the same for your own messages
- `src/net/protocol.js` + `server/src/protocol.js` — **`GEAR`** carries weapon/pet/mount ids in BOTH directions, sent only when they change (the client de-duplicates, so main.js can safely call `net.gear()` every frame) — a weapon id is a string and paying for it 8×/s to say "still the same sword" would be absurd
- **THE PORT 443 TRAP**: some hosts run an allowlist you cannot change. Symptom: port 80 works, Let's Encrypt succeeds, Caddy answers 308, and 443 times out with no TLS handshake — everything inside the VPS is correct, which sends you looking there for hours. `server/deploy/setup-tunnel.sh` sidesteps it: cloudflared dials OUT, so no inbound port exists to block
- **`lighting.state` is `minutes`, not `time`.** Three call sites used the wrong name and silently evaluated `undefined / 60` → NaN, so every night check read as day and night-only fish and dailies could never fire

### Solo vs online

The menu has **two doors, not one**: NEW ADVENTURE / CONTINUE build a private world, and **🌐 PLAY ONLINE** (shown only when `VITE_GAME_SERVER` is set) connects to the shared one. `main.js` gates `serverConfigured()` behind that choice — having a server configured must never push somebody into a world with strangers in it. Going online with a hero already made carries that hero in rather than forcing character creation again. Signed-in players also get **DELETE PROFILE** in the account strip: two-step (the button changes to REALLY DELETE? and re-arms after 4s), removes the Supabase `saves` row via `deleteCloudSave()` (RLS restricts it to the owner) AND the local save, because otherwise CONTINUE would resurrect what was just deleted.

## Conventions

- All in-game text & code comments are in English — including anything a third party renders for us. Google's sign-in button localises itself from the browser's language, which put one Indonesian string in the middle of an otherwise English game; the fix is `?hl=en` on the **GIS script URL**, not the `locale` option on `renderButton`, which does not override a script that has already resolved its language
- Never add image/audio asset files — everything stays procedural (canvas/WebAudio) per the original design. The ONLY exceptions are the two branding images in `logoasset/` (logo + creator mascot)
- Color palette is locked in `PALETTE` (src/gfx/textures.js) — keep the cozy 2.5D voxel style consistent
- `window.__semesta` exposes the live systems for automated verification

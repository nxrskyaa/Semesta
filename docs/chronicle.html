A note on what this document does not do

It does not argue that Semesta should be a financial product. The game is finished and it is fun without a token; that is the strongest possible position from which to add one, and the fastest way to lose it is to bolt on mechanics that make the game worse in order to make the asset tradeable. Every recommendation here is tested against one question: does the game survive this change if the token goes to zero? Where the answer is no, the recommendation is not made.

The discipline this document tries to hold

Semesta's own in-game guide currently tells players, in plain language, that nothing is on-chain yet and that anyone asking them to connect a wallet today is not the team. That sentence was written deliberately. Nothing proposed here should be announced before it is true, and the guide should keep saying exactly what is and is not live at every stage.

Section 01

Semesta already runs, off-chain, the exact machinery Rialo makes native

This is not a game looking for a chain. It is a game that has already built — in JavaScript, in a browser, against a wall clock — six workarounds that Rialo replaces with primitives.
The answer, first

Go to Rialo, and go for the execution model rather than for the token. Semesta's distinguishing systems are all asynchronous: a house that finishes building in four hours whether or not the tab is open, a season that rolls over on a fixed calendar with no server told to do it, a world boss on a timer, crops that grow while you are elsewhere. On every other chain those are off-chain keepers, cron jobs and indexers — the “fragile tower” Rialo's own research names as the core problem. On Rialo they are conditional transactions and native workflows.

The token is the last reason to go, not the first. The first is that the game's architecture already has the right shape.

Why the fit matters more than it sounds

Most games arriving on-chain are asked to become something they are not: to add a marketplace, a staking screen and a daily-login token in order to justify the ledger. Semesta needs none of that, because the parts of it that are hard to run — the timers, the shared clock, the season boundary, the account — are the parts Rialo is built to run. The chain is being asked to do infrastructure work, which is the only job it is unambiguously good at.

Put another way: the honest reason to deploy is that the game currently asks players to trust a VPS, a browser's clock and a Postgres row. Every one of those is a promise the team is making personally. On Rialo, three of them stop being promises.

Section 02

The boundary is the design; almost every failed on-chain game drew it wrong

Nothing that runs at sixty frames per second goes on a ledger. What goes on the ledger is what must survive the studio.
The answer, first

Put ownership, scarcity and the shared clock on-chain. Leave simulation, progression and all per-frame state off it. The test is not “can this be on-chain” — almost anything can. The test is “does this need to outlive us, or be provable to a stranger?” A player's mythic weapon does. Their current stamina does not.

Exhibit 2
Draw the line at “must outlive the studio”, not at “could technically be written to state”
On-chain — must outlive us
  • Asset ownership. Which account holds which limited cosmetic, mythic weapon or pass.
  • Issuance & supply. How many of each limited piece exist, and the rule that mints them.
  • The season clock. Which season it is, when it ends, and the reward set bound to it.
  • Long timers. Homestead construction, prestige caches, crop maturity.
  • Achievement proof. First clears of the Hollow's six bosses; Index category completion.
  • Identity. The account, its three character slots, and the link to a sign-in.
  • Token ledger. Balances, sinks, and any transfer.
Off-chain — would only make it worse
  • Everything per-frame. Position, facing, animation, camera, the 8 Hz position feed.
  • Combat resolution. Monster HP, aggro, damage rolls, the 20 species' AI.
  • Hero progression. Level, XP, attribute points, skill trees. Not scarce, not tradeable, not interesting to a stranger.
  • The world itself. 200 cells of terrain generated from a seed. Storing it would be paying to keep a pure function.
  • Consumables and gold. Tonics, brews, forge stones, coins. Unlimited faucet by design.
  • Quest and story state. Personal, not scarce.
  • Cosmetic appearance data. The art is procedural and regenerates from an id.
The rule that decides the hard cases: if a player would be angry to lose it when the servers close, it goes left. If they would not notice, it goes right.
Note the asymmetry in cost. Moving something left buys durability and pays in latency, fees and complexity. Moving something right buys speed and pays in trust. Semesta's combat is 60 fps client-authoritative today; nothing in this document changes that.
The failure mode to avoid, stated plainly

The common mistake is to put progression on-chain because it looks like ownership. It is not. Levels, skill points and quest flags are personal bookkeeping with no counterparty; putting them on a ledger adds a signature prompt to every kill and buys nothing. The games that did this are the ones players describe as “a wallet with a game attached”. Semesta's own guide already draws this distinction correctly for pass XP versus hero XP; the same instinct applies here.

What the boundary implies for the client

Semesta's renderer, physics and combat stay exactly as they are. The on-chain layer sits beside them and is consulted at four moments only: when an asset is granted, when an asset is spent or burned, when a timer is started or read, and when the season turns. Everything else in the game never touches it. That is a small enough surface that it can be added without rewriting the game, and — equally important — removed again if the chain is the wrong bet.

Section 03

Five programs, not one; the state stays small because the world is a seed

The whole on-chain footprint of a 200-cell open world with 203 items fits in five programs, because none of them stores a world.
The answer, first

Split by lifetime, not by feature. Registry and Ledger change rarely and must never be lost. Season and Timers churn every block. Identity is read constantly and written almost never. Bundling them produces one program that is simultaneously hot, precious and unupgradeable — the shape that forces teams into risky migrations later.

Rialo VM is RISC-V with SVM compatibility today and EVM/MoveVM signalled to follow, so the implementation language is a decision that can be deferred past the architecture. That is a genuine advantage: the split above does not depend on which one is chosen.

The state-size argument, quantified

The reason this is affordable is that Semesta already refuses to store its world. Terrain, decor, camps, chests and landmark placement are all derived from fixed seeds, which is why the multiplayer server can be “one small box” and why the map is never sent over the wire. The same property carries on-chain: the ledger stores which account owns item id X, never what item X looks like, where it is, or what the ground beneath it is made of. The art regenerates from the id on the client, procedurally, in a 16-pixel canvas.

A consequence worth stating out loud

Because the art is procedural and the id is the asset, a Semesta NFT does not need image hosting, IPFS pinning, or a metadata gateway — the three things that quietly break most NFT collections within a few years. The token points at an id in the Registry; any client that can run the game can draw it. This is an accident of the original “never add asset files” house rule, and it is worth a great deal.

Reactive transactions, in the game's own vocabulary

The predicate sits on-chain and is evaluated at the end of each block by every validator. No keeper, no cron, no server. The player closes the tab.

The condition becomes true. The associated transaction is enqueued by consensus and executed. The house exists whether or not anyone is looking.

Next session, the client reads state directly from validators and raises the villa. The scaffolding it replaces is already in the game.

The same four steps describe the season rollover, a prestige cache, a crop reaching stage three, and the 180-second world boss. One primitive, four features — which is what Rialo's research calls supermodularity, and is the practical reason to prefer it here.
Section 04

Three classes of asset, and a four-question test before anything becomes one

Semesta has 203 items. Roughly twenty-three of them should ever be tokens. The discipline is in the refusals.
The answer, first

Tokenise proof and scarcity; refuse to tokenise inventory. Three classes: soulbound for things that are proof of what a player did, tradeable for things that are genuinely scarce and genuinely someone else's to want, and off-chain for everything else — which is the large majority, and should stay that way.

The on-chain test

An item becomes an NFT only if it passes all four. Any one failure and it stays an ordinary game item.

1Is supply genuinely limited? Not “rare drop”. Limited by a rule that can be stated in one sentence and checked by a stranger. Semesta already tags three such sets: Lanterns (8), The Hollow (9), Keeper's Vault (6).
2Would anyone want it who did not earn it? A cosmetic passes. A stack of forge stones does not — it is a commodity with an unlimited faucet, and tokenising commodities is how game economies inflate.
3Does trading it damage the game? If an item is the reward for a fight, and it can be bought instead, the fight is now optional. This is the question that sends most weapons to the off-chain column.
4Does it still make sense if the market is dead? The asset must be worth owning for what it does in the game, with zero bid. If the only reason to want it is resale, it is not a game asset.

Why the Vault is the right first collection

Most NFT drops have to invent a scarcity story. The Vault's is already true and already shipped: six pieces, no duplicates ever, a currency that has no price because it cannot be bought, and a set that completes in exactly six tokens. A player who owns all six this season owns proof of a finished season. Season two rotates the set, which makes season one's set permanently closed — without anyone having to promise it will be.

Section 05

Two currencies with a firewall between them, and sinks that already outnumber faucets

The single most common cause of death in GameFi is an unlimited faucet wired to a market. Semesta's protection is to never connect them.
The answer, first

Gold stays soft, infinite and off-chain. $SEMESTA stays hard, capped and on-chain. There is no exchange rate between them, in either direction, ever. Gold buys consumables, farm plots, boat keys and season passes. $SEMESTA does exactly three things: it mints limited assets, it settles trades between players, and it pays for seasonal entry. A player who never touches it can still finish the pass, clear the Hollow and complete the Index.

Exhibit 6
The firewall is the whole design: grinding produces gold, and gold can never become the token
Gold — soft currency, unchanged

Faucets: monster drops, fishing, farming, chests, quests, the pass track, daily check-in, level rewards. Effectively unlimited.

Sinks that already exist: gacha (100c, or 900c for ten), forging +1…+9 with failure, seeds, tonics, brews at 220–260c, farm plots, the 480c Donut Boat key, house tiers at 200c and 600c, and both season passes at 1,000c and 3,000c.

Status: a working closed loop. It needs no chain and gets none.

$SEMESTA — hard currency, capped

Faucets: seasonal emission only, distributed against the pass track and Hollow clears. Emission per season is fixed in advance and declines on a published schedule.

Sinks: minting a Vault piece, trading fees, seasonal entry for the on-chain track, and burning on pass activation.

Status: does not exist yet. Nothing below should be announced as if it does.

No swap. No conversion. No “gold to token” rate at any point — that single link is what turns a game economy into a farm.
The asymmetry is deliberate and worth defending under pressure: gold is allowed to inflate because it buys only things the game prints. The token is not allowed to inflate because it buys things the game cannot reprint.

The Keeper's Token is already the right bridge, and it was not designed to be

The pass currently pays a currency — the Keeper's Token — that cannot be purchased at any price. Its only sources are the reward track (2 on the free row, 5 with Basic, 10 with Premium) and the endless prestige caches past tier 50. It buys only Vault pieces, and the Vault never repeats.

That is, structurally, a mint pass. It has a supply that is a function of play, a sink that consumes it, and a distribution curve that already separates free players from paying ones without locking anyone out. The on-chain version should change nothing about how it is earned; it should only make the resulting asset real.

Where the published roadmap needs revisiting

The in-game roadmap currently lists “Hold to Play — minimum 1,000 SEMESTA” as phase two. This should be cut. It contradicts the game's own strongest design principle — the free reward row exists specifically so that nobody is locked out — and it converts the top of the funnel into a purchase decision made before the player has seen anything. A holding gate also produces the worst possible first impression in a market already suspicious of exactly this pattern.

If holders need a benefit, give them one that is additive rather than exclusionary: a cosmetic frame, priority in a queue, a seasonal title. The difference between “holders get something extra” and “non-holders get nothing” is the difference between a game with a token and a token with a game.

Section 06

Four releases, each of which is worth shipping even if the next one never happens

The testnet is live now. The correct first release contains no token and no NFT.
The answer, first

Ship identity first, assets second, market third, token last. Each release is independently valuable, independently reversible, and does not require believing the next one will work. A team that ships the token first has spent its credibility before it has proved it can run a chain integration at all.

What can start this week

The Playground already demonstrates the exact onboarding Semesta needs — sign in with Google, receive a custodial testnet wallet, hold a points balance that persists across apps in a shared catalogue. Semesta's account layer is a near-identical shape and already routes every entry through a sign-in. R1 is therefore not a research project; it is a substitution.

The second thing that can start immediately is a supply page. Before any asset is tradeable, publish how many of each limited piece exist and the rule that mints them. Doing this before there is a market is what separates a collection from a promise.

Section 07

What actually kills this, ranked, and what to do about each

Two of the top three risks are not technical, and none of the top three is “the chain goes down”.
The answer, first

The largest risk is that the token makes the game worse. Semesta is finished and enjoyable now; the failure mode is not a hack, it is a series of small concessions that turn a game people play into a yield product people leave. Every control below is a way of noticing that early.

Exhibit 9

Risks 1 and 2 are the ones to re-read before every release. They are also the two that no amount of engineering will fix after the fact.
A test to apply before each release

Show the build to somebody who does not own crypto and does not intend to. If their experience of the game got worse in any way — an extra click, a wallet prompt, a screen they must dismiss, a reward they can no longer reach — the release is not ready, regardless of what it does for holders. Semesta's audience is players first; the guide, the prologue and the free reward row all already assume that.

Appendix A

Open questions for Rialo engineering

These are the answers that would change the architecture above. They are worth asking before R1, not during it.
#QuestionWhy it changes the design
1What is the cost and latency ceiling of a conditional transaction that sleeps for 12 hours? The villa build is 12 h. If long-lived predicates are priced per block evaluated rather than per trigger, the timer design changes shape entirely
2How many predicates can one account hold concurrently? A busy player has a house timer, up to 8 crop timers and a prestige counter at once — roughly 10 per account, times the player base
3Is there a per-block cap on triggered transactions, and what happens on the season boundary when every player's season predicate fires in the same block? This is the one genuinely adversarial moment in the design: a synchronised global trigger. If it needs smoothing, the season rollover must be staggered per account
4What are the guarantees and the rate limit on Rialo Edge HTTPS calls from a contract? Determines whether the multiplayer server can be retired or must remain
5Does Rialo IPC expose the Playground's Google-to-custodial-wallet flow as a reusable primitive, or is that Playground application code? R1 is a substitution if the former and a build if the latter. This is the single highest-value answer on this page
6Is on-chain randomness available to contracts, and is it manipulable by a proposer? The gacha stays off-chain in this plan, so this is not blocking — but it determines whether it ever could move
7What is the migration story for the Registry as items are added — does Gauss-style upgrade apply to application programs or only to the protocol? Semesta ships new items regularly. A catalogue that cannot grow is a catalogue that forces a redeploy
8What does Rialo Cruise gasless transaction sponsorship cost the sponsoring application? Players must never see a gas prompt for claiming a pass tier. If sponsorship is affordable, the UX problem disappears
9Is there a testnet reset schedule, and what survives one? Genesis Lanternkeepers minted in R1 are a promise to early players. If testnet state is wiped, that promise must be honoured off-chain and re-minted
